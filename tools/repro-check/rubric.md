# Rubric: is this reproduction package ready to post?

Grade the package, not the prose. Length, confidence, template headings, and a polished tone never decide a check. Each check reads a concrete outcome against the issue.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the issue body and the repo-facts block (the version, OS, and any driver, shell, or build profile the issue says the behavior depends on). | Pass only if the report states the tool version and the OS, plus any driver, shell, or build profile the issue itself says changes the behavior. A log line that implies an OS is not a record, and a profile inferred from which error appeared is not a record. If the tested version, OS, shell, or driver is not the one the issue says the bug was confirmed on (including "latest" or "main" in the issue, compared with the latest release in repo facts), the report must say they differ. Naming the difference passes, including an honest cannot-reproduce. Silence on a real gap fails: recording "pandas 1.5.3" does not pass when the issue says the bug was confirmed on the latest release and main. | required |
| steps-followable | The repro report's steps, read against the trigger in the issue (the command, input document, expression, flag, or condition that produces the behavior). | Pass if a stranger can carry out the issue's trigger from the written steps alone. A documented equivalent that still hits the same trigger passes (an offline flag that prints the same request, a current version of the same command). Fail if the steps are missing; if they omit a flag or condition the issue's own steps include (the driver, the shell, the language order); if they swap the trigger for a lookalike that fails earlier (a start:end range where the issue uses an offset-from-end range, a colon where the issue has `=`, an unbound name where the issue binds one); or if the report says the repo or config cannot be shared. An honest cannot-reproduce passes when the steps show the attempt at the issue's trigger. | required |
| behavior-shown | The pasted artifacts in the repro report (command output, logs, console text, measurements), read against the specific symptom the issue names. | Pass if the artifact shows that symptom: the named error text, missing field, wrong value, panic, crash, or empty result. An adjacent symptom fails even when the report calls it the bug: a usage or validation error is not a panic; a compile error about an unbound name is not the reported path error; a syntax error that asks for a different token is not a panic; a version banner, a session list, or "the tabs are visible" is not a blank pane; escape-sequence text with the process still running and the prompt returning is not a crash. A root-cause paragraph with no pasted output is not an artifact, so it fails. Also pass, without showing the bug, when the report says it could not reproduce, the artifact shows what actually happened, and the report names what differed from the issue's conditions or what a triggering setup still needs. | required |
| outcome-honest | The report's stated result (reproduced, cannot reproduce, or the named symptom), read against the artifact in the same report. | Pass if those words describe the artifact. "Could not reproduce," backed by the negative result, passes. Fail if the report calls the artifact the issue's crash, panic, or bug when the artifact is a different error, a process that stayed alive, or only proof that the tool started. Fail if expected and actual are swapped relative to the pasted output. Confidence words ("exactly as described", "100% reproducible") do not create a match the artifact does not have. | required |
| claim-specific | The candidate claim comment, read against the issue's specific behavior. | Pass if the comment names this issue's concrete symptom, file, or next experiment in words that would not fit an unrelated issue unchanged. A short comment passes. Fail a bare +1 or me-too that only says "this" and names no next step. Fail assign-me boilerplate that promises a fix by a deadline ("within 2 days guaranteed", "keep this issue reserved") and does not name the bug. Do not fail a comment for being modest, informal, or from a first-time contributor. | required |
| ai-disclosure | The repo-facts contribution policy, read against the claim comment and the repro report. | Pass when the policy does not require disclosing AI use in issue comments. "No stated AI policy", a responsibility rule ("you must understand your code"), "low-quality AI content is closed", "comments must be written by a human", and "no disclosure ask for issue comments" are not disclosure requirements, and a pull-request-only rule does not apply to these comments. Fail only when the policy says AI usage must be disclosed, or must state the tool and the extent, for issues, comments, or any form of contribution, and neither comment contains an explicit disclosure (AI was used, plus the tool or the extent). These packages are AI-assisted work: human-sounding prose is not a disclosure, and silence fails that requirement. A disclosure in either comment is enough. | required |
| no-guaranteed-deadline | The claim comment only. | Pass if the comment does not promise a fix by a calendar deadline or call the fix guaranteed. | preferred |

## Verdict rule

Accept only if every required check passes. A preferred check never changes the verdict, whether it passes or fails. Reject if any required check fails. `unclear` counts as fail: proof you cannot find is not ready to post. There is no third verdict.
