# Rubric: is this plan ready to post and build from?

Grade the plan and the plan comment, not the prose. Length, confidence, headings, and a polished tone never decide a check. Each check reads a concrete outcome against the package.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause-grounded | The candidate plan's stated cause (the Diagnosis section, or the line or paragraph that says what causes the bug), read against the Repro evidence section, including every control run, timing, and artifact there. | Pass only if the plan states a cause and that cause is the behavior the repro actually shows. A control rules that cause out only when the blamed component is still on the path that showed the symptom, or is off that path and the symptom remains. A control the repro itself says fits, because that run took a different path (a fresh attach instead of reattach, an older version from before the blamed path existed, or an empty cache that refetches on the fresh-attach path), does not rule the cause out. Fail a tokenizer blamed for items that parse when the same items are sent with no extra flag, and the debug trace shows argparse rejecting them before the item parser runs. Fail a missing-module cause when the same build still prints that module's error for a sibling call. Fail a post-read cast when the artifact shows the values already gone in the inferred table before any cast. Fail a pager key-binding cause when the same wait remains with paging turned off and disappears with highlighting turned off. Fail when the plan gives no cause and says only to investigate, profile, or figure out what happened. | required |
| scope-bounded | The candidate plan's scope: the Scope section, or the In and Out lines, or the list of proposed changes, read against the single symptom in the issue and the Repro evidence. | Pass if every change the plan will actually make serves that one symptom, and any larger idea is explicitly not in scope or deferred. A second site of the same bug in the same function, checked and reported rather than redesigned, still passes. Deferring a larger rework (a tombstone rewrite, a direct-globset migration, an untestable platform variant) while shipping the change the repro isolates passes. Fail when the plan will also do independent work the issue did not ask for, even if the direct fix is included: a dependency migration, a new settings panel or option, a subsystem or state-machine rewrite, a new abstraction across runtimes, a CI redesign, a retry framework, or a campaign of several such fronts. | required |
| executable | The candidate plan's approach and the files or sites it names (the Files section, the Approach, or the Change paragraph). | Pass if a stranger could start the change from the text: it names a file, module, or specific site, and it says what to change there. Naming the area and the change is enough when the exact function is explicitly left to a trace the plan already describes. Fail when no file or site is named, or the action is only to investigate, profile, look into, optimize whatever turns up, add a recover somewhere, or fix it upstream or vendored whichever is easier, with the real edit deferred. | required |
| test-decisive | The candidate plan's test plan (the Test plan section, or the Test line), read against the symptom and the steps in the Repro evidence. | Pass if the test would show that symptom gone, by naming an observable result: a specific output, an exit code, an assertion, or the repro step's expected after-state. A manual re-run of the repro with that expected result passes. Fail if the test only checks a nearby fact (bindings registered, the suite stays green, a new setting round-trips) and never checks the reported symptom. Fail a feeling ("should feel fast", "look much better", "nothing else should feel broken") and fail "run the full test suite" or "CI passes" when no check of this bug's own symptom is named. | required |
| thread-convention | The candidate plan comment, read against the Thread highlights and the repo-facts contribution-policy line. | Pass the thread half when no OWNER, MEMBER, COLLABORATOR, or CONTRIBUTOR highlight names a file, function, constant, or approach to use or to avoid, and none posts a patch or binary and asks for it to be tested. When such a direction is present, pass only if the comment names that artifact and says it is following it, narrowing it, or deliberately not following it. A comment that only restates a different plan and never names the directed file, function, approach, or test request fails. Pass the policy half when the policy does not require disclosing AI use in issue comments. "No stated AI policy", a responsibility rule ("you must understand your code"), "low-quality AI content is closed", "comments must be written by a human", "assistive AI is allowed", and "no disclosure ask for issue comments" are not disclosure requirements, and a pull-request-only rule does not apply to these comments. Fail the policy half only when the policy says AI usage must be disclosed, or must state the tool and the extent, for issues, comments, or any form of contribution, and the plan comment contains no explicit disclosure (AI was used, plus the tool or the extent). These packages are AI-assisted work: human-sounding prose is not a disclosure, and silence fails that requirement. Both halves must pass. | required |
| unknowns-labeled | The candidate plan's risk or unknown lines, when it has any. | Pass if a stated unknown is labeled as unknown or deferred, or if the plan states no uncertain claim. Fail if a measurement or decision the plan says it has not made is written as already settled. This check never changes the verdict. | preferred |

## Verdict rule

Accept only if every required check passes. A preferred check never changes the verdict, whether it passes or fails. Reject if any required check fails. `unclear` counts as fail: a plan you cannot verify from the package is not ready to build from. There is no third verdict.
