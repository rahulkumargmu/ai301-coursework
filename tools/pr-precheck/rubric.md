# Rubric: is this pull request ready to submit?

Grade the diff, the test evidence, and the description against the plan and the repo's stated asks. Length, confidence, heading polish, and commit-message tone never decide a check.

The four required checks are the four ways a bad PR gets submitted: silent drift, not tested, unreviewable, and standards wall. A PR that honestly records a shortfall in the plan and restates it in the description can still be ready. A PR that claims work the diff does not contain, or hides an extra change, is not.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The plan-context scope and Files list, any "not in scope" or "deliberately deferred" sentence, and any deviation note in the plan or the description, read side by side with every file in the diff and with the description's fidelity sentences ("exactly", "in full", "no changes beyond", "no functional changes outside"). | Pass when every changed file is one the plan names, or sits in a folder the plan names as the place for that change (its tests, its changelog entry). A deliverable the plan names may be absent only when the plan itself defers it and the description restates that same deferral. Extra work the description discloses as a deviation, with a reason, passes. Fail when the diff changes a file or behavior the plan does not name and does not disclose: a new option or flag, a config setting, an unrelated rewrite, or a drive-by edit in another file. Fail when the description claims the plan was implemented exactly, in full, or with nothing beyond it, and the diff either contains that extra change or lacks a deliverable the plan did not defer. | required |
| test-decisive | The plan's test plan read against the candidate PR's Test evidence section. The bug repro is the command the test plan says to re-run for the reported failure. A control, a suite command, or a happy-path check is not a second bug repro. | Pass when that bug repro is shown and its result is specific: printed output, an exit code, an error string, or a before/after written on the command, including after `#` or `--`. A control or a suite may be one sentence ("control unchanged", "pytest passes", "covered by the new test") once the bug repro itself is shown. Fail when the evidence never shows the bug repro and only says "tested locally", "works now", "verified on my machine", or "tests pass". Fail when the commands shown are only a control the plan says does not hit the bug. Fail when the test plan names two separate bug reproductions (two commands that each trigger the failure, such as repro 1 and repro 2) and one of those commands never appears. An honest pasted failure, with the reason, passes. Hiding it does not. | required |
| diff-reviewable | The unified diff and the commit list, read for leftover debris rather than for whether the fix matches the plan. | Pass when a reviewer can see the fix without leftover debugging. Fail when the diff contains a debug print left in (`DEBUG`, `eprintln!`, `dbg!`, `console.log`, `print(` used as a probe), a commented-out earlier attempt, a dead function (`unused`, `allow(dead_code)`, a name like `_unused`), a TODO stuck on an import or a leftover, or a hunk that only reindents, reflows, or reprints identical lines. A real behavior change the plan did not ask for is plan-fidelity, not this check, unless it is also one of those debris tells. Commit subjects alone do not fail this check. | required |
| standards-met | The repo-facts pull-requests line and contribution-policy line, read against the description and, for a required changelog or whatsnew file, against the diff. | Pass when every concrete ask in that pull-requests line is present: a required issue reference (`Closes #`, `fixes #`, `closes #xxxx`) contains a number; each named template section has real content or an explicit N/A with a reason; a required changelog or whatsnew entry appears in the diff. When the line says there is no PR template, do not invent sections. Pass a missing AI sentence when the policy says "no stated AI policy". Fail when a required issue reference, checklist, or changelog/whatsnew file is absent. Fail when the policy says AI usage must be disclosed (the tool, the extent, or all AI usage) and the description never states that AI was used. These packages are AI-assisted: human-sounding prose is not a disclosure. A policy that only asks maintainers' comments to be human-written passes when the description says the words are the author's own or states the AI use. Do not fail a vouch flow, a CLA, or "keep the PR small" from the package text alone. | required |

## Verdict rule

Accept only if every required check passes. Reject if any required check is fail or unclear. There is no preferred check and no third verdict. `unclear` counts as fail: a PR you cannot verify from the package is not ready to submit.
